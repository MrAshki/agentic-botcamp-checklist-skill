# محتوای اصلی جلسه ۳

## ۱. محصول AI فقط مدل نیست

### محتوای دوره

یک محصول واقعی از چند لایه تشکیل می‌شود:

- Frontend برای تعامل کاربر
- API و منطق برنامه
- لایه Agentic شامل مدل، RAG، ابزار، حافظه، Guardrail و Router
- لایه داده شامل پایگاه داده رابطه‌ای، برداری، فایل و Cache
- اتصال به سامانه‌های دیگر
- زیرساخت، استقرار و MLOps
- امنیت، حاکمیت و مشاهده‌پذیری

مدل فقط خروجی تولید می‌کند. Agent می‌تواند هدف را دنبال کند و ابزار به‌کار ببرد. نرم‌افزار مدل یا Agent را در یک گردش‌کار قابل‌استفاده قرار می‌دهد. محصول زمانی شکل می‌گیرد که این نرم‌افزار یک نیاز انسانی را با تجربه کاربری، پشتیبانی، امنیت و عملیات مناسب حل کند.

## ۲. اجزای Agentic Workflow

نمونه گردش‌کار جلسه این اجزا را نشان می‌دهد:

1. Trigger و ورودی
2. Context و داده
3. برنامه‌ریزی و انتخاب مسیر
4. هماهنگ‌سازی نقش‌ها یا متخصص‌ها
5. فراخوانی ابزار و یکپارچه‌سازی
6. Guardrail و Governance
7. ارزیابی و بازبینی انسانی
8. اجرا و اقدام
9. حافظه و وضعیت
10. پایش، ثبت خطا، تأخیر، هزینه و Trace

این اجزا الزام نمی‌کنند که همه پروژه‌ها Agent خودمختار داشته باشند. اگر مسیر ثابت است، Workflow کنترل‌شده انتخاب ساده‌تری است.

## ۳. سطح بلوغ محصول

- POC: اثبات امکان فنی با کمترین دامنه
- Prototype: نمایش شکل تعامل و تجربه کاربر
- MVP: کمترین محصولی که برای کاربر واقعی ارزش می‌سازد
- Product: سامانه پایدار با امنیت، پایش، پشتیبانی و عملیات

هر سطح پرسش و ریسک متفاوت دارد. POC پاسخ می‌دهد «آیا شدنی است؟». Prototype تجربه را آزمایش می‌کند. MVP ارزش و استفاده واقعی را می‌سنجد. Product به قابلیت اطمینان و نگهداری نیاز دارد.

## ۴. روش ساخت

در Waterfall، نیازها و مراحل از ابتدا با ترتیب مشخص تعریف می‌شوند. در Agile، محصول به بخش‌های کوچک تقسیم می‌شود و با بازخورد پیوسته رشد می‌کند. برای محصول AI، عدم قطعیت داده و مدل باعث می‌شود ساخت افزایشی، ارزیابی مداوم و ثبت نتیجه هر مرحله مهم باشند.

## ۵. Frontend و تجربه کاربر

Frontend بخشی است که کاربر می‌بیند و لمس می‌کند. HTML ساختار، CSS ظاهر و JavaScript رفتار را می‌سازد. UI ظاهر و اجزای تعامل است. UX کیفیت تجربه کامل کاربر است.

در محصول AI باید این موارد نیز روشن باشند:

- وضعیت انتظار و پردازش
- منبع و استناد پاسخ
- خطا، عدم اطمینان و محدودیت
- امکان بازبینی و اصلاح
- تفاوت داده منبع با خروجی مدل

## ۶. داده و پایگاه داده

DBMS ذخیره، جست‌وجو، تراکنش، دسترسی و پشتیبان‌گیری را مدیریت می‌کند.

- پایگاه رابطه‌ای برای داده ساختاریافته و رابطه‌های روشن مناسب است.
- Document DB برای سندهای JSON و Schema منعطف کاربرد دارد.
- Key-value برای Cache و Session مناسب است.
- Graph DB رابطه‌های شبکه‌ای را مدل می‌کند.
- Vector DB برای بازیابی بر اساس شباهت معنایی استفاده می‌شود.
- Warehouse برای تحلیل و گزارش در مقیاس سازمانی است.

در پروژه جلسه، PostgreSQL داده برنامه، Session و Audit را نگه می‌دارد و افزونه pgvector بردارها را در همان سامانه ذخیره و جست‌وجو می‌کند.

## ۷. Backend و عملیات

Backend شامل API، منطق کسب‌وکار، دسترسی به داده، کارهای پس‌زمینه و اتصال به سرویس‌های بیرونی است. مسیر CI/CD نشان‌داده‌شده شامل کد، آزمون، ارزیابی LLM، Build، Registry، Staging و Production است. بازگشت به نسخه پایدار باید ممکن باشد.

پایش فقط Log نیست. Metrics، Trace، خطا، تأخیر، هزینه و کیفیت خروجی نیز باید ثبت شوند.

## ۸. نمونه آموزشی جلسه

MindEvidence Lab یک دستیار پژوهشی RAG برای دانشجویان روان‌شناسی است. دانشجو پرونده‌های کاملا مصنوعی را بررسی می‌کند و درباره درمان اعتیاد پرسش می‌پرسد. سامانه در اسناد مجاز جست‌وجو می‌کند و پاسخ مستند می‌دهد.

مرزهای نمونه:

- بیمارها و پرونده‌ها ساختگی هستند.
- سامانه برای آموزش است.
- سامانه تشخیص، تجویز یا انتخاب درمان انجام نمی‌دهد.
- داده پرونده، شواهد پژوهشی و تفسیر مدل جدا نمایش داده می‌شوند.
- تصمیم نهایی با درمانگر است.
- هر مرحله در Audit Log ثبت می‌شود.
