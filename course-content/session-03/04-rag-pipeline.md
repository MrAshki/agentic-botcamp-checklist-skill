# محدودیت‌های LLM و خط لوله RAG

## چرا LLM به‌تنهایی کافی نیست؟

محدودیت‌های مطرح‌شده در جلسه:

- Knowledge Cutoff و نداشتن دانش تازه
- Context Window محدود
- Hallucination
- نداشتن دسترسی خودکار به داده خصوصی
- نداشتن منبع و استناد قابل‌پیگیری
- هزینه Fine-tune و نامناسب‌بودن آن برای هر تغییر محتوا
- دشواری کنترل سطح دسترسی
- وابستگی به ورودی و امکان دستور مخرب در داده بازیابی‌شده

RAG دانش بیرونی را هنگام پاسخ بازیابی می‌کند. این روش تضمین نمی‌کند که پاسخ همیشه درست است. کیفیت ورود اسناد، قطعه‌بندی، embedding، بازیابی، ساخت Context و ارزیابی بر نتیجه اثر دارند.

## مرحله Offline: ورود و نمایه‌سازی

1. سندهای مجاز و معتبر انتخاب می‌شوند.
2. متن و Metadata مانند عنوان، بخش، صفحه و منبع استخراج می‌شوند.
3. متن با مرزهای معنادار به Chunk تقسیم می‌شود.
4. برای هر Chunk یک Embedding ساخته می‌شود.
5. متن، Metadata و بردار در ذخیره‌ساز ثبت می‌شوند.
6. خطاهای استخراج، سند تکراری و نسخه سند کنترل می‌شوند.

در نمونه جلسه، اندازه تقریبی Chunk برابر ۴۰۰ تا ۷۰۰ Token است. این مقدار یک تنظیم پروژه‌ای است و قانون ثابت نیست.

## مرحله Online: بازیابی و تولید

1. پرسش کاربر دریافت و اعتبارسنجی می‌شود.
2. پرسش به embedding تبدیل می‌شود.
3. Chunkهای نزدیک با جست‌وجوی برداری و فیلتر Metadata بازیابی می‌شوند.
4. در صورت نیاز، نتیجه‌ها بازرتبه‌بندی می‌شوند.
5. Context Builder فقط شواهد مناسب را وارد Prompt می‌کند.
6. مدل بر پایه پرسش و Context پاسخ می‌دهد.
7. پاسخ به Chunk و منبع واقعی استناد می‌کند.
8. اگر شواهد کافی نیست، سامانه باید این موضوع را اعلام کند.

## پایگاه داده برداری

Embedding یک بردار عددی از معنای متن است. فاصله یا شباهت بردارها برای یافتن متن‌های مرتبط استفاده می‌شود. گزینه‌های مطرح‌شده شامل pgvector، Qdrant، Milvus، Weaviate و Pinecone هستند. انتخاب ابزار به مقیاس، عملیات، بودجه و معماری موجود بستگی دارد.

برای پروژه کوچک، افزودن pgvector به PostgreSQL می‌تواند معماری را ساده نگه دارد. وجود Vector DB به‌تنهایی RAG خوب نمی‌سازد.

## کنترل کیفیت RAG

- مجموعه پرسش و پاسخ ارزیابی بسازید.
- Recall بازیابی را جدا از کیفیت پاسخ بسنجید.
- استناد باید به Chunk واقعی و محل سند اشاره کند.
- Patient fact، Research evidence و Model interpretation را جدا نگه دارید.
- داده بازیابی‌شده را داده نامطمئن در نظر بگیرید؛ نه دستور سیستم.
- Prompt Injection داخل سند را کنترل کنید.
- سطح دسترسی را پیش از بازیابی اعمال کنید.
- پاسخ بدون شواهد را با حدس پر نکنید.
- تغییر مدل، Prompt، Chunking یا embedding را با ارزیابی ثابت مقایسه کنید.

## RAG، Fine-tune یا Prompt

- Prompt برای تغییر رفتار و قالب پاسخ مناسب است.
- RAG برای دانش بیرونی، تازه، خصوصی یا قابل‌استناد مناسب است.
- Fine-tune برای تغییر پایدار رفتار یا سبک و برخی وظایف تخصصی کاربرد دارد؛ نه برای واردکردن مداوم اسناد تازه.

ممکن است پروژه فقط به یکی از این روش‌ها نیاز داشته باشد.
