
# چک‌لیست‌های جامع بوت‌کمپ هوش مصنوعی

---

## چک‌لیست ۱: یک مسئلهٔ واقعی را چطور مدل کنیم؟

### ۱. مسئله و ارزش
- [ ] چه تصمیمی بهتر می‌شود؟ معیار موفقیت (KPI) و هزینه خطا چیست؟
- [ ] راه‌حل بدون AI چقدر خوب است؟ این Baseline شماست.
- [ ] قیدها: بودجه، تأخیر، حریم خصوصی، قانون، تحریم
- [ ] AI را فقط جایی بگذارید که ارزش اضافه دارد.

### ۲. نوع مسئله
- [ ] عدد ← رگرسیون؛ دسته ← طبقه‌بندی؛ بی‌برچسب ← خوشه‌بندی
- [ ] داده جدولی ← اول XGBoost؛ تصویر، صوت، گراف: خانواده مدل خودشان
- [ ] تولید و استخراج ← LLM؛ چندقدمی ← Workflow یا Agent

### ۳. داده
- [ ] منبع، مجوز، حجم و کیفیت برچسب را پیش از مدل بسنجید.
- [ ] EDA: Missing، Outlier، تکراری، چولگی
- [ ] Train / Validation / Test جدا؛ مراقب Data Leakage
- [ ] PII، رضایت و Data Dictionary از همان اول

### ۴. مدل و ارزیابی
- [ ] از ساده‌ترین مدل شروع؛ هر پیچیدگی را Eval توجیه کند.
- [ ] معیار متناسب: F1/PR برای نامتوازن، RMSE/MAE برای عدد
- [ ] Cross-Validation و بررسی Overfitting
- [ ] LLM: Golden Set، Eval مسیر و نتیجه

### ۵. استقرار و پایش
- [ ] Spec اول؛ Git و Docker از قدم اول
- [ ] نسخه‌بندی داده، مدل و Prompt؛ Rollback
- [ ] Shadow ← Canary ← Production
- [ ] پایش کیفیت، هزینه، Drift؛ مالک و Kill Switch

### ۶. انسان و مسئولیت
- [ ] جایی که خطا گران یا برگشت‌ناپذیر است، انسان تأیید می‌کند.
- [ ] توضیح‌پذیری: شواهد، ارجاع، SHAP
- [ ] سوگیری را برای هر گروه جدا بسنجید.
- [ ] اگر Eval بهبود نشان نداد، «نساختن» هم نتیجه خوبی است.

## چک‌لیست ۳: انتخاب مدل (API یا محلی، بزرگ یا کوچک)

### ۱. ده معیار انتخابی
- [ ] کیفیت روی Golden Set خودتان
- [ ] Tool Calling و JSON پایدار در حلقه‌های طولانی
- [ ] کیفیت فارسی (حتماً تست کنید)
- [ ] Context کافی (برای اسناد، حداقل 32K)
- [ ] هزینه به‌ازای وظیفه و تأخیر P95
- [ ] مجوز: Apache/MIT برای کار سازمانی
- [ ] حریم خصوصی و محل نگهداری داده
- [ ] سخت‌افزار و حافظه، پایداری نسخه، پشتیبانی

### ۲. API یا محلی؟
- [ ] API: کیفیت بالاتر، بدون سخت‌افزار، بار کم یا نامنظم، نمونه‌سازی
- [ ] محلی: داده حساس، حجم بالا و ثابت، آفلاین یا تحریم، کنترل نسخه، Fine-tune
- [ ] هزینه پنهان محلی: GPU، عملیات، به‌روزرسانی، امنیت
- [ ] نقطه سربه‌سر را با عدد حساب کنید، نه با حس
- [ ] ترکیبی: Gateway مثل LiteLLM و Fallback بین مدل‌ها

### ۳. اندازه و معماری مدل
- [ ] کوچک برای مسیریابی، استخراج و دسته‌بندی؛ بزرگ برای استدلال، تحلیل و برنامه‌ریزی
- [ ] MoE: حافظه زیاد، سرعت خوب؛ Dense: ساده و قابل‌پیش‌بینی
- [ ] حافظه ≈ پارامتر × بایت + ۲۰٪ + KV Cache
- [ ] سرعت ≈ پهنای باند ÷ حجم مدل
- [ ] Q4_K_M پیش‌فرض خوب؛ Q8 اگر حافظه دارید

### روش پیشنهادی
- [ ] ۳ کاندید از Leaderboard و جامعه انتخاب کنید.
- [ ] Golden Set با ۳۰ تا ۱۰۰ نمونه واقعی بسازید.
- [ ] کیفیت، هزینه و تأخیر را مقایسه کنید.
- [ ] تصمیم را ثبت کنید.
- [ ] با هر نسخه جدید، ارزیابی را تکرار کنید.

- [ ] Golden Set با ۳۰ تا ۱۰۰ نمونه واقعی؛ در CI اجرا شود.
- [ ] سطوح: Unit، Trajectory، Outcome، Safety، Human Review
- [ ] LLM-as-Judge فقط با کالیبراسیون و بازبینی انسانی
- [ ] معیار Tool Calling و پایداری در حلقه طولانی
- [ ] تعداد قدم، توکن و هزینه به‌ازای وظیفه

### ۳. کیفیت در Production
- [ ] بازخورد کاربر (👍 / 👎)، نرخ ویرایش و نرخ ارجاع به انسان
- [ ] Latency (P50، P95)، نرخ خطا، نرخ Timeout
- [ ] هزینه روزانه، بودجه و هشدار
- [ ] بازبینی نمونه‌ای هفتگی و بازنویسی Golden Set از خطاهای واقعی

### ۴. دروازه انتشار
- [ ] هر تغییر مدل یا Prompt باید از Golden Set و Eval امنیتی عبور کند.
- [ ] Canary ← Shadow ← کامل؛ شرط بازگشت از قبل نوشته شود.
